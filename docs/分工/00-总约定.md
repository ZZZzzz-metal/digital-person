## 5. 共享类型（B 维护 `src/b2_core/contracts.py`）

以下是内部 v0.1 合同。官方适配由 B 做字段映射，不能把它直接称为官方协议。JSON 字段统一 snake_case，ID 为字符串，时间为 UTC ISO 8601（`Z` 结尾），页面按北京时间展示。

```python
from typing import Literal
from pydantic import BaseModel, Field

Emotion = Literal['neutral', 'happy', 'sad', 'anxious', 'angry', 'unknown']
Expression = Literal['neutral', 'smile', 'concern', 'listening']

class Message(BaseModel):
    role: Literal['user', 'assistant']
    content: str

class MemoryItem(BaseModel):
    id: str
    key: str                     # 如 preferred_name、exam_subject
    value: str
    updated_at: str

class MemoryContext(BaseModel):
    prompt_text: str = ''
    retrieved_memories: list[MemoryItem] = Field(default_factory=list)

class CoreRequest(BaseModel):
    messages: list[Message]      # 最后一条必须是本轮 user；不得追加两次
    memory_context: str = ''
    persona: str = '伴学：中文日常陪伴助手'
    max_new_tokens: int = 256
    temperature: float = 0.3

class CoreReply(BaseModel):
    reply: str
    emotion: Emotion = 'unknown'
    expression: Expression = 'listening'
    model_version: str
    is_mock: bool = False

class ChatRequest(BaseModel):
    session_id: str
    client_turn_id: str          # C 每次发送生成一个；同次重试不换
    text: str

class ChatResponse(BaseModel):
    session_id: str
    client_turn_id: str
    reply: str
    emotion: Emotion
    expression: Expression
    retrieved_memories: list[MemoryItem]
    model_version: str
    elapsed_ms: int
    is_mock: bool

class SessionDTO(BaseModel):
    id: str
    title: str
    created_at: str
```

前端类型由 C 按 B 的 schema 生成或逐字段复制，以 schema 验证样例。`retrieved_memories` 表示本轮检索到的候选，不证明模型确实使用了每一项；界面名称用“本轮参考记忆”。情绪只是模型估计，用户界面不要呈现为心理诊断。

最小 JSON 样例：

```json
{
  "session_id": "session-demo-1",
  "client_turn_id": "turn-demo-1",
  "reply": "听起来你对这次考试有些担心。你愿意先说说最让你困扰的部分吗？",
  "emotion": "anxious",
  "expression": "concern",
  "retrieved_memories": [],
  "model_version": "baseline-v1",
  "elapsed_ms": 1200,
  "is_mock": false
}
```

这里的回复和耗时仅为协议样例，不是实测效果或性能。

## 6. 数据和记忆约定

B 建库，A 不直接写数据库，C 不直接读数据库。

| 表 | 必须字段 | 规则 |
|---|---|---|
| users | id, memory_enabled, created_at | 演示 API 首次访问分配随机匿名用户 cookie |
| sessions | id, user_id, title, created_at | 所有查询和删除都检查 cookie 用户归属 |
| messages | id, session_id, role, content, created_at | 成功推理后才原子写入本轮 user/assistant |
| memories | id, user_id, key, value, updated_at | `(user_id,key)` 唯一；用户确认的新值替换旧值 |
| turns | session_id, client_turn_id, response_json | 二者联合唯一；同次重试返回已完成结果 |

### 短期历史

最近 12 条已完成消息，最多约 4,000 中文字符；加当前用户输入后还须通过 A 的 tokenizer 检查模型上下文长度。超长时从最旧完整轮次开始移除，不截断当前问题。用户输入为空或超过 2,000 字符时 API 返回 400。

### 长期记忆

演示最小版只保存用户**主动确认**的事实：称呼、学习目标、偏好。内部 v0.1 key 白名单固定为 `preferred_name`（称呼）、`study_goal`（学习目标）、`exam_subject`（关注的考试科目）、`response_preference`（回应偏好）、`hobby`（兴趣）；前端使用选择项，不任意造 key。C 提供“保存为记忆”和修改/删除按钮，B 提供 CRUD；A 可以提出候选但不能绕过用户确认直接持久化。不得把情绪推断和健康诊断当作事实记忆。

记忆检索先按字段关键词与当前话题匹配，最多 5 项；不相关记忆不塞进 prompt。数据按 user_id 隔离，跨会话可复用，同名 key 更新值即可完成纠正。记忆关闭时不读取、不保存；关闭不等于删除，界面另有“清空记忆”。

**官方自动测评中的记忆**：以官方显式提供的历史/记忆字段为边界。没有用户标识与跨轮机制时，每个独立样本新建 `InMemoryStore`，不能复用演示数据库或把前一个样本记忆带给下一个。官方提供明确会话边界时才按其规则维护状态。

### 官方训练与验证切片（A 实施，B 提供核对依据）

原始每行是 `conversation_id + turns + prediction_points`，不是一条现成的 ChatRequest。对每个标注预测点，输入只保留截至 `target_user_turn_id`（包含本轮 user）的历史，监督输出来自该点 `target`。`assistant_response_turn_id` 用于检查标注关联；该回复、后续 turns、情绪/画像参考标签和参考 `memory_refs` 均不得进入推理输入。不要直接把整段会话当 prompt，这会带入答案。

### B2 存储与匿名身份合同（2026-10-10）

- 本轮实现四个会话路由：POST/GET `/api/sessions`、GET `/api/sessions/:id/messages`、DELETE `/api/sessions/:id`；成功 JSON 沿用 B1 schema，不改 A/C 的共享字段。`/api/chat` 和 memory HTTP 接口仍等 B3/B4。
- cookie 名 `b2_anon`，服务端生成随机不透明 token；存储只保存 token 的 SHA-256 与独立随机 user_id 的映射。未知、伪造或直接填 user_id 的 cookie 会创建新匿名身份，不能指定他人的 user_id。cookie 为 HttpOnly、SameSite=Lax、Path=/；本机默认 Secure=false，HTTPS 可用 B2_COOKIE_SECURE=1。身份仅为本机匿名演示，不是完整账号系统。
- 默认 SQLite 文件 `.runtime/b2.sqlite3`，可用 B2_DB_PATH 指定本项目数据文件。API 从服务端身份取 user_id，所有会话/消息操作检查归属；不存在与不属当前用户统一 404。参数错误按总约定返回 400/error 对象。健康查询不创建匿名用户。
- 共享存储区域 `src/b2_core/store.py` 提供 SQLiteStore/InMemoryStore 及同一 Store 协议：resolve_user、create_session、list_sessions、get_messages、delete_session、reserve_turn、complete_turn、abort_turn、close。create_session/list/get/delete 接受服务端 user_id；HTTP 客户端不能传它。
- resolve_user 返回 AnonymousIdentity(user_id,cookie_token)，cookie_token 只在新身份时返回以设置 cookie；已有合法 token 返回 None。所有 DTO 返回独立副本。
- reserve_turn(user_id,session_id,client_turn_id) 返回 TurnReservation(user_id,session_id,client_turn_id,token,lease_expires_at)，或已完成的原 ChatResponse。一个会话只允许一个 pending；正在执行时抛 TurnInProgress（未来聊天 API 映射为 409），不同会话互不阻塞。按 `(session_id,client_turn_id)` 去重，不按文本去重。
- complete_turn(reservation,user_text,response) 返回 None，在一次事务中保存 user/assistant 两条 Message 和完整 ChatResponse，再标记 turn 完成；先验证 ID、文本与 DTO，任何异常全部回滚。同一个成功 reservation 再 complete 不改旧结果；重试通过 reserve 返回原 ChatResponse。abort_turn 仅释放匹配 token 的 pending。reserve/complete/abort 不调用模型，B2 以虚构测试 fixture 验证失败不写入；模型 HTTP 编排由 B4 接入。
- pending 默认租期 300 秒，过期后允许重新占用，旧 token 不能再提交或释放新占用；租期是内部演示恢复策略，不是官方推理限制。模型调用期间不持有 SQLite 写事务。删除先检查归属；有有效 pending 时返回 409，过期 pending 可清理后删除。成功删除同时删 messages/turns，不触碰未来用户级长期记忆。
- SQLite 使用外键级联、短写事务和每会话 pending 唯一约束，支持线程及两个 store 实例对同一文件竞争；close 后文件可重新打开，已完成 turn 可重试。应用仅关闭自己创建的 store，注入 store 的生命周期由调用方管理。
- InMemoryStore 为每个实例独立的 SQLite `:memory:` 数据库，复用相同事务实现；关闭后不保留数据，不会复用演示文件。Store 错误提供 code/message，包含 ResourceNotFound、TurnInProgress、StoreBusy、StoreClosed 和 StaleReservation；HTTP 归属错误统一 NOT_FOUND。

### B3 记忆存储与检索合同（2026-10-10，A/C 合并拉取同步）

- HTTP 沿用上表五个记忆操作及 B1 的 MemoryItem/MemoryList/schema，字段不变；`/api/chat` 仍待 B4。保存只发生在用户主动 PUT 时，不从会话、情绪或画像自动提取落库。
- Store 新增 `list_memories(user_id) -> MemoryList`、`set_memory_enabled(user_id,enabled:bool) -> MemoryList`、`save_memory(user_id,key:MemoryKey,value:str) -> MemoryItem`、`delete_memory(user_id,memory_id) -> None`、`clear_memories(user_id) -> None`。返回独立 DTO 副本，SQLite/InMemoryStore 语义相同。
- 记忆挂在用户而非会话上；`(user_id,key)` 唯一。同 key 保存使用稳定 id 原地替换 value/updated_at，旧值不保留在检索结果；删除后再保存生成新 id。value 去首尾空白后必须为 1–200 字符的非空字符串，key 只允许五个约定字段。
- 关闭后 list/settings 返回 `enabled=false,items=[]`，不读取记忆值；save 返回 409 `MEMORY_DISABLED`，不改数据库。事实保留，重新开启后可见。用户明确删除/清空是关闭状态下允许的管理动作，仍检查归属；清空不改 enabled，不删其他用户。未知 id 与他人 id 同为 404。
- 开关、更新、删除、清空均在短事务内完成；可在旧 B2 数据库上增加 memories 表而不重建 users/sessions/messages/turns。客户端不能传 user_id 或 timestamp/id，沿用 b2_anon cookie。
- `build_memory_context(user_text,memories)` 为纯函数，无数据库、HTTP 或模型调用。调用者必须传当前用户 `list_memories(...).items`（关闭时为空）；按字段话题关键词或值的有意义词匹配，最多五项，返回 `MemoryContext` 和独立候选 DTO。问及考试时只带当前 exam_subject；无关宿舍话题不会带考试科目。短词/通用词不作任意命中。
- prompt 使用有明确说明的 JSON 用户事实数据，不将 value 拼成系统指令；候选列表称“本轮参考记忆”，不宣称模型已经引用。此包装不能保证模型对提示注入完全免疫，真实模型效果由后续阶段实测。没有相关项时 prompt_text 为空。
- B3 通过存储/API 和构造 CoreRequest 的 fixture 验证高数→线代、跨会话、关闭与用户隔离；不是聊天模型生成或正式离线测评通过。A 接收 MemoryContext 文本，C 接收上述固定 API 和 MEMORY_DISABLED 错误即可，不新增共享 DTO 字段。

### B4 聊天编排与失败重试合同（2026-10-10，A/C 合并拉取同步）

- 新增 POST `/api/chat`，沿用 ChatRequest/ChatResponse 及现有 schema，不新增字段。先检查 cookie 归属并 reserve turn；已成功的同 turn 返回完整原响应，不再次调用模型/写消息，文本不同也不覆盖该成功结果。同文本但新 turn_id 是新的发送。
- `build_core_request(user_text,history,memory_context='') -> CoreRequest` 为 B 的纯历史构造函数：校验历史为完整 user/assistant 轮次，取最近最多12条历史，超过4000字符就从最旧完整轮开始移除，最后追加当前输入一次；不截断当前输入。A 继续用 tokenizer 控制实际模型上下文。HTTP 从当前用户的 enabled memory 取得相关事实，关闭或不相关时为空。
- `run_turn(request,engine) -> CoreReply` 仅重新验证/复制输入、调用一次 generate 并验证输出，不读 store、不启动服务/浏览器/模型、不追加历史。允许共享 DTO、同字段 model_dump/asdict 对象或字典输出；成功回复须非空字符串，is_mock 为严格 bool、model_version 非空并与 engine metadata 一致。情绪枚举异常归 unknown，表情枚举异常归 neutral；缺省合法值沿用 DTO，不用固定文本替换失败。
- engine 在应用启动时仅初始化一次；真实模式缺实现/资产或生成失败均明确失败，不转 stub。B 的演示 stub 始终 is_mock=true。elapsed_ms 用单调时钟实测本轮构造/生成/提交前耗时，重试返回原值，候选记忆不代表模型确实引用。
- 同会话有效 pending 为409 TURN_IN_PROGRESS；同一进程的共享 engine 同时最多一次 generate，另一个会话在占用期间返回503 MODEL_BUSY，释放其 turn 便于原ID重试。模型不可用/错误输出/异常为503 MODEL_UNAVAILABLE；演示生成超时为503 MODEL_TIMEOUT。C 对这些失败保留输入与 client_turn_id。
- 演示超时由 B2_CHAT_TIMEOUT_SECONDS 配置，默认60秒，必须为有限正数且最多240秒，低于默认300秒 turn 租期；create_app 的测试注入参数名 chat_timeout_seconds。此限制只用于演示HTTP，不是官方测评超时。worker 仅做纯生成，HTTP 成功后才原子 complete；失败/超时/取消 abort，不能保存半个轮次。
- Python 线程超时不能强制杀死正在执行的模型计算：HTTP及时返回503，迟到结果丢弃且不写库；全局 engine gate 直到该计算实际结束才释放，避免并发调用同一模型。若模型一直不返回，需要停止/重启该演示进程。应用退出关闭自建worker，不关闭别人的服务；不宣称线程已被硬终止。
- B4 区分真实A引擎运行、明确stub/fixture编排验收、C前端联调、正式GPU禁网容器。缺某项时准确记录，继续完成不依赖它的工作；本轮不生成官方提交结果，也不把 mock 冒充真实六轮。

Mock 模式：A 的 engine 返回 `is_mock=true`，C 本地 mock 同样返回 true，并显示“演示数据”。真实模式不允许自动悄悄退回 mock。

## 10. 全 AI 并行流程

1. 三个 Agent 使用独立分支/独立工作目录，避免同一份 Git 工作区切来切去。Agent 不在共享目录同时安装依赖、改锁文件或创建提交。
2. B 先提交 contracts 和自身骨架；A、C 同时在各自目录开工。拉取共同骨架后，各自继续，不等待对方完成 P1。
3. 每完成一个可运行任务就提交。提交说明写“完成什么、运行了什么检查、还有什么阻塞”。按队伍当前约定，Agent 推送分支并创建 PR；用户手动合并和拉取，Agent 不代替执行。合并冲突由文件主人修，其他任务继续。
4. 共享接口变更：提出问题 → B 改合同与 schema → A/C 同步 → 再改实现。不得先改代码再要求别人猜。
5. Agent 默认自主解决可逆的实现选择；缺账号、缺官方文件、确有权限阻塞时才列出需要人的具体操作。禁止编造测评通过、训练收益、商业数据和提交成功。
6. 不做大规模评测或反复调 UI。每次集成至少检查：能启动、一次聊天、记忆保存/调用/纠正、错误状态、官方入口或其待核实事项。
7. 硬件不足时缩小模型、数据量和上下文，先导出可运行基线；不能把云 API 改成离线测评的替代方案。
