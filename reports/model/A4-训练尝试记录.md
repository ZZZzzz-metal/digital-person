# A4 训练尝试记录

**结论：完成了一次受预算约束的小规模本地适配。能保存、能重载、能评测，且完全可复现（两次运行权重逐位相同）。
但规模极小——6 次 optimizer step——不代表能力有明显提升。**

> ⚠️ **本机没有 GPU。** `torch.cuda.is_available() == False`，无 `nvidia-smi`。
> 所以 A4 的「最多 6 GPU 卡时」在实际执行中**消耗 0 卡时**——它是 CPU 上跑的。
> 20 卡时券对应的实例需要队长在咪咕仝学平台创建并提供访问权限，A 无法自行登录。
> 这是当前唯一的硬阻塞，已如实记录，**没有假装用满了预算**。

## 做法

| 项 | 值 |
| --- | --- |
| 基础模型 | Qwen2.5-0.5B-Instruct（Apache-2.0，494,032,768 参数，fp32） |
| 训练方式 | **只训练最后 4 层 Transformer + 最终 norm**，其余 20 层冻结 |
| 可训练参数 | **59,650,432 / 494,032,768 = 12.07%** |
| 数据 | `data/training/processed/train.jsonl`（200 条：chat 150 + official 50） |
| 验证 | `data/training/processed/valid.jsonl`（120 条） |
| `max_len` | 448 |
| 实际训练样本 | 200 条，**超长丢弃 0 条**（超长时裁剪最旧轮次：36 条被裁剪，25 条验证样本被裁剪） |
| 平均长度 | 320.0 tokens |
| 学习率 | 5e-05，5 步 warmup + 线性衰减 |
| 批大小 | `micro_batch 8` × `grad_accum 8` = **有效批 64 条** |
| 步数 | **6 次 optimizer step**（≈1.9 个 epoch，上限 30 步 / 40 分钟，都未触及） |
| 耗时 | **7.33 分钟**（平均 8.8 s/step） |
| 设备 | CPU，16 线程 |
| GPU 卡时 | **0** |
| 随机种子 | 20261010 |

**为什么只训练最后 4 层**：494M 参数的全参 fp32 AdamW 大约需要 12 GB 内存，
而本机可用内存只有约 15.1 GB，全参会把机器压到危险边缘。
只训练最后 4 层 + norm 后，可训练参数降到 5,965 万，稳定跑完。
这是一个**明确缩小的适配范围**，不是完整的 SFT。

## 保存与重载（硬性验证）

只凭训练日志不能宣称推理可用，所以脚本在保存后**必须重新加载并生成**才写报告：

```json
"reload_check": {
  "attempted": true,
  "loaded": true,
  "params": 494032768,
  "probe_reply": "你今天还好吗？",
  "probe_non_empty": true
}
```

- 保存的是**完整 fp32 全量权重**（1,976,163,472 B）+ config + tokenizer，
  **不是 LoRA/适配器**，`model_dir` 指过去就能当普通模型加载。
- `tie_word_embeddings=true` 时 `lm_head` 与 `embed_tokens` 共享存储，
  safetensors 拒绝保存共享存储，所以**只保存 `embed_tokens`**，加载时按 config 自动重新绑定。
  已记录在 `training_meta.json` 的 `tied_tensors_dropped`。
- 保存格式：先跑了 1 步的冒烟训练（[a4_training_smoke.json](a4_training_smoke.json)），
  确认保存与重载都通过后才跑正式训练。

## 可复现性（实测）

同一个种子连跑两次正式训练，产出的权重**逐位相同**：

```
run1 sha256 6fb4dd30f4f2714811c4b612c40fc4d46348eb67debbf2cfde5ade2a63541985
run3 sha256 6fb4dd30f4f2714811c4b612c40fc4d46348eb67debbf2cfde5ade2a63541985
```

loss 序列也完全一致（3.138122 / 2.194058）。因此 `weights/sft-short/` 是确定性的产物，
B 重跑 `training/train_sft.py` 应当得到同一份权重。

## 这次踩到的坑（如实记录）

| 问题 | 处理 |
| --- | --- |
| 第一版人设提示词 **221 tokens**，导致 200 条样本里 **152 条**编码超过 `max_len` 被丢弃 | 把提示词压到 **106 tokens**，并把「超长就丢样本」改成「裁剪最旧的完整轮次」，200 条全部可用 |
| `max_len 512` 时每步约 95 s（同时还有并发的评测在抢 CPU） | 降到 448 并把训练与评测串行，每步降到 8.8 s |
| 保存时报 `Some tensors share memory` | 检测共享存储，只保存 `embed_tokens` |
| 报告里 `effective_batch` 写成了 8（实际是 64） | 修正口径：显式区分 `micro_batch` 与 `grad_accum`，重跑并确认权重不变 |

## 必须一起看的限制

1. **6 次 optimizer step、200 条模板化合成样本**，规模极小。它证明了链路可跑通，
   **不能证明能力有实质提升**。
2. **只训练最后 4 层**，是内存约束下的缩小方案，不是完整 SFT。
3. 标签来自**规则标注**，不是人工标注、也不是官方标签。
4. **没有 GPU，0 卡时**；A4 要求的「最多 6 GPU 卡时」在本机无法执行。
5. 本机**没有跑过官方 `start.sh`**，也没有官方成绩。
